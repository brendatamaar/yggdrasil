# Builds — Model Functional Effect design

Covers BL-03 (ordered steps, stop at first failure, one build at a time), BL-04 (Maven dependency ordering), BL-05 (presets), BL-06 (live logs, history), BL-07 (artifacts) and BL-09 (builds in a worktree). Toolchain detection (BL-10) and module commands (BL-01, BL-02, BL-11, BL-15) produce the `StepSpec`s this design runs, but are designed separately: they are stateless file readers.

Fixed decisions are in `docs/phases/phase-2.md` → "Pre-phase fixes" → Decisions.

> Note: `docs/PLAN.md` labels Maven ordering as BL-02. The PRD's ID for it is **BL-04**; BL-02 is the Node module.

Core package: `internal/core/builds` (pure, no JSON tags). Shell: `internal/builds` (service, interpreter, worker), `internal/db` (rows ↔ state), `internal/api` (DTOs, handlers).

## State map

Per build: a sealed `builds.State`.

```go
type State interface{ isState() }

type None struct{}                       // before Enqueue
type Queued struct {
    ID       core.BuildID
    Spec     Spec                        // target + ordered StepSpecs
    QueuedAt time.Time
    Actor    core.Actor                  // user | agent:<name> | system
}
type Running struct {
    ID        core.BuildID
    Spec      Spec
    QueuedAt  time.Time
    StartedAt time.Time
    Steps     []StepState                // len == len(Spec.Steps)
    Current   int                        // index of the one StepRunning
}
type Cancelling struct {                 // kill sent, waiting for the process to exit
    Running                              // same data; Steps[Current] is StepRunning
    CancelledAt time.Time
}
type Finished struct {
    ID         core.BuildID
    Spec       Spec
    QueuedAt   time.Time
    StartedAt  *time.Time                // nil when cancelled while queued
    FinishedAt time.Time
    Steps      []StepState               // none Pending or Running
    Result     Result
    Artifacts  []Artifact                // nil until collected; empty slice = none found
}
```

Step state (sealed `StepState`):

```go
type StepPending struct{}
type StepRunning struct{ Attempt int; StartedAt time.Time }
type StepDone    struct{ Attempt int; StartedAt, FinishedAt time.Time; Outcome Outcome; LogTruncated bool }
type StepSkipped struct{}                // never ran: an earlier step failed, or the build was cancelled
```

`Outcome` (sealed): `Succeeded{}` · `Failed{ExitCode int}` · `StartFailed{Reason StartFailure}` · `Cancelled{}` · `Interrupted{}`.
`StartFailure` (string enum with `Validate`): `not_found` · `bad_args` · `dir_missing` · `other`.

`Result` (sealed): `ResultSucceeded{}` · `ResultFailed{Step int}` · `ResultCancelled{}` · `ResultInterrupted{Step int}`.

The derived status, `Status(State) core.BuildStatus`, is stored in `builds.status` for queries only. The status set gains `interrupted`, and step status gains `skipped` and `interrupted`.

There is no separate "retrying" or "timed out" state: there are no step retries and no step timeouts at v1 (see Open questions). "Empty" is not a state: a `Spec` with zero steps is rejected at the boundary.

Queue: not an aggregate. The queue is the set of `Queued` builds. Admission is decided by the pure function `Next(queued []QueuedRef, running int, max int) (core.BuildID, bool)`, with `max = 1` (BL-03).

## Inputs

All inputs carry `Now time.Time`. IDs are generated by the shell.

| Input | From | Fields |
|---|---|---|
| `Enqueue` | user (UI, palette), preset run, agent (later MCP) | `ID, Spec, Actor, Now` |
| `Admit` | queue worker after `Next` picks this build | `Now` |
| `StepExited` | interpreter: the process ended | `Index, Attempt, ExitCode int, LogTruncated bool, Now` |
| `StepStartFailed` | interpreter: the process could not start | `Index, Attempt, Reason StartFailure, Now` |
| `Cancel` | user | `Actor, Now` |
| `ProcessLost` | startup reconciliation, for builds found `Running`/`Cancelling` | `Now` |
| `ArtifactsCollected` | interpreter: result of `CollectArtifacts` | `Artifacts []Artifact, Now` |

## Transition table

Notation: `i` = `Current`, `n` = `len(Steps)`, `a` = attempt of `Steps[i]`. Every changing transition also emits `WriteAudit` and `Publish(BuildChanged)`; this is listed only where the audit action matters.

| From | Input | Guard | To | Commands |
|---|---|---|---|---|
| None | Enqueue | `Spec` valid (≥1 step) | Queued | `WriteAudit(build.queue)`, `Publish`, `Wake` |
| Queued | Admit | — | Running{Current 0, Steps[0]=Running{1, Now}, rest Pending, StartedAt Now} | `WriteAudit(build.start)`, `StartStep(0, 1)`, `Publish` |
| Queued | Cancel | — | Finished{ResultCancelled, StartedAt nil, all Skipped} | `WriteAudit(build.cancel)`, `Publish`, `Wake` |
| Running | StepExited | `Index==i ∧ Attempt==a ∧ ExitCode==0 ∧ i+1<n` | Running{Steps[i]=Done(Succeeded), Steps[i+1]=Running{1, Now}, Current i+1} | `WriteAudit(build.step)`, `StartStep(i+1, 1)`, `Publish` |
| Running | StepExited | `Index==i ∧ Attempt==a ∧ ExitCode==0 ∧ i+1==n` | Finished{ResultSucceeded} | `WriteAudit(build.finish)`, `CollectArtifacts`, `Publish`, `Wake` |
| Running | StepExited | `Index==i ∧ Attempt==a ∧ ExitCode≠0` | Finished{ResultFailed{i}, Steps[i]=Done(Failed{code}), later Skipped} | `WriteAudit(build.finish)`, `Publish`, `Wake` |
| Running | StepStartFailed | `Index==i ∧ Attempt==a` | Finished{ResultFailed{i}, Steps[i]=Done(StartFailed{r}), later Skipped} | `WriteAudit(build.finish)`, `Publish`, `Wake` |
| Running | Cancel | — | Cancelling{CancelledAt Now} | `WriteAudit(build.cancel)`, `KillStep(i, a)`, `Publish` |
| Running | ProcessLost | — | Finished{ResultInterrupted{i}, Steps[i]=Done(Interrupted), later Skipped} | `WriteAudit(build.interrupted)`, `Publish`, `Wake` |
| Cancelling | StepExited / StepStartFailed | `Index==i ∧ Attempt==a` | Finished{ResultCancelled, Steps[i]=Done(Cancelled), later Skipped} | `WriteAudit(build.finish)`, `Publish`, `Wake` |
| Cancelling | ProcessLost | — | Finished{ResultCancelled, Steps[i]=Done(Cancelled), later Skipped} | `WriteAudit(build.finish)`, `Publish`, `Wake` |
| Finished | ArtifactsCollected | `Result==Succeeded ∧ Artifacts==nil` | Finished{Artifacts} | `WriteAudit(build.artifacts)`, `Publish` |

**Any other (state, input) pair: no change, no commands.** This includes:

- a stale `StepExited`/`StepStartFailed` (wrong index or attempt);
- `Cancel` on `Cancelling` or `Finished`;
- `Admit` on anything but `Queued`;
- `Enqueue` on anything but `None`;
- a second `ArtifactsCollected`.

A Running step whose exit code is 0 while the build is `Cancelling` still ends as `Cancelled`: the user asked for it.

`Attempt` is 1 for every step at v1. It exists so that a later "retry from failed step" (or any duplicate delivery) cannot be confused with the current run. The key of a step run is `(BuildID, Index, Attempt)`.

## Invariants

Each one is checked after every step of a random input sequence (`run(None, inputs)`), with `rapid` generators that mix legal, stale and duplicate inputs.

| # | Invariant | Property test |
|---|---|---|
| I1 | In `Running`/`Cancelling`: exactly one step is `StepRunning` and it is `Steps[Current]`; every step before it is `Done(Succeeded)`; every step after it is `Pending`. | `TestPropRunningShape` |
| I2 | In `Finished`: no step is `Pending` or `Running`. `Queued` has no step state. | `TestPropFinishedHasNoLiveStep` |
| I3 | Over a whole run, the `StartStep` commands for a build have indices 0, 1, 2, … in order, each `(Index, Attempt)` at most once. | `TestPropStepsStartInOrderOnce` |
| I4 | Stop at first failure: if a step is `Done` with an outcome other than `Succeeded`, every later step is `Skipped` and the state is `Finished`. | `TestPropStopsAtFirstFailure` |
| I5 | Stale inputs are no-ops: `StepExited`/`StepStartFailed` whose `(Index, Attempt)` is not the current running step returns the same state and no commands. | `TestPropStaleInputIsNoop` |
| I6 | No `StartStep` after `Cancel`: once a `Cancel` input has been applied to a non-Finished build, no later step emits `StartStep`, and the build ends `ResultCancelled`. | `TestPropNoStartAfterCancel` |
| I7 | `Finished` is terminal: no input moves it to another variant, and no input emits `StartStep` or `KillStep` from it. | `TestPropFinishedIsTerminal` |
| I8 | `Status(state)` agrees with the steps: `succeeded` ⇔ every step is `Done(Succeeded)`. | `TestPropStatusDerived` |
| I9 | Every step that changes the state emits exactly one `WriteAudit`; a step that doesn't change it emits nothing. | `TestPropAuditPerChange` |
| I10 | Times come only from inputs, and for every `StepDone`, `StartedAt ≤ FinishedAt` when input times are non-decreasing. | `TestPropTimesFromInputs` |
| Q1 | `Next` never admits when `running ≥ max`. It picks the oldest `(QueuedAt, ID)`. Its result is a member of `queued`. | `TestPropNextFIFO` |
| O1 | `OrderModules`: the output is a permutation of the input repos. For every dependency edge `a → b` not inside a cycle, `b` comes before `a`. Every cycle is reported once. The output is deterministic for a given input. | `TestPropOrderTopological` |

## Commands

| Command | Cardinality | Idempotent | Produces |
|---|---|---|---|
| `WriteAudit{Action, Subject, Detail}` | one | yes: written in the same `Store.Commit` as the state, never after | — |
| `Publish{BuildChanged}` | one, after commit | yes: subscribers refetch by build ID | — |
| `Wake` | one, after commit | yes: coalesced; tells the queue worker to re-run `Next` | `Admit` to the chosen build |
| `StartStep{BuildID, Index, Attempt, Target, Argv, TaskID?}` | one start, then a **stream** of log lines, then one exit | **no**: starts a process. Key `(BuildID, Index, Attempt)`; the interpreter refuses a second start for a key it has already started | `StepExited` or `StepStartFailed` |
| `KillStep{BuildID, Index, Attempt}` | one | yes: cancels the step's ctx; a no-op if it has already exited or is unknown | none directly (the `StepExited` follows) |
| `CollectArtifacts{BuildID, Target, RepoIDs}` | one | yes: read-only glob of the toolchain's artifact patterns | `ArtifactsCollected` |

## Call graph

```go
// Production
HTTP POST /api/builds  |  POST /api/build-presets/{id}/run
  → guard (Host/Origin) → decodeBody
  → builds.ParseRequest (boundary) → builds.Spec, or 400 with the rule broken
  → BuildService.Enqueue(ctx, spec, actor)          // api-side interface (review item 11)
      → handle(id, Enqueue{ID: ids.New("bld"), Spec, Actor, Now: clock.Now()})

handle(buildID, input)                              // internal/builds; all inputs go through one goroutine
  → Store.Commit(ctx, func(tx) {                    // one BEGIN IMMEDIATE
        state, version ← tx.LoadBuild(buildID)      // rows → State (boundary parser)
        state2, cmds  ← corebuilds.Step(state, input)   [core]
        tx.SaveBuild(state2, version)               // WHERE version = ? → db.ErrConflict on mismatch
        tx.AppendAudit(audit.Prepare(cmd, redactor, ids.New("aud"), Now))  for each WriteAudit
    })
  → interpret effect commands (after commit, outside the tx):
      StartStep → resolve argv[0] (platform.Resolve, repo dir: mvnw.cmd, npm.cmd, …)
                → open log file <dataDir>/logs/builds/<buildID>/<index>-<attempt>.log
                → start(ctx_step, platform.Spec{Argv, Dir, Env: safety.Clean(), TaskID?, Stdout/Stderr: redacting line writer → file + hub})
                → goroutine (owned by the service errgroup): Wait → enqueue StepExited
                  (start error → StepStartFailed with the reason classified)
      KillStep  → cancel ctx_step                   // platform kills that process's own job only
      CollectArtifacts → toolchain.Artifacts(repo) globs → os.Stat → enqueue ArtifactsCollected
      Publish   → hub.publishNext(BuildTopic{ID}, BuildChanged) and hub.publishNext(BuildsTopic{}, BuildChanged)
      Wake      → queueWorker.wake()

queueWorker (one goroutine)
  → on wake: refs ← store.ListQueued ; running ← store.CountRunning
  → corebuilds.Next(refs, running, 1) [core] → handle(id, Admit{Now})

startup (cmd/ygg newApp, before serving)
  → for each build in store.ListActive (Running|Cancelling): handle(id, ProcessLost{Now})
  → queueWorker.wake()

HTTP POST /api/builds/{id}/cancel → BuildService.Cancel → handle(id, Cancel{Actor, Now})
GET  /api/builds, /api/builds/{id}         → store reads → api DTO
GET  /api/builds/{id}/steps/{i}/log?after= → log file read (range)
WS   build:<id>                            → BuildChanged + log lines (stream, seq per topic)
```

## Failures

| Node | Failure | Class | Handling |
|---|---|---|---|
| ParseRequest | empty steps, unknown repo, worktree not of repo, empty argv, NUL, shell metacharacter (`platform.BatchArgsOK`) | domain outcome | 400 with the rule in plain language; nothing stored |
| Store.Commit | `db.ErrConflict` (version mismatch) | retry | reload and re-run `Step` once. A second conflict is a bug (the single input goroutine should prevent it) → die (logged, input dropped, build left as stored) |
| Store.Commit | `db.ErrNotFound` on load for an input other than Enqueue | domain outcome | input ignored (build deleted or never existed); 404 at the API |
| Store.Commit | SQLite busy/IO | die for this input | error logged; API 503 "try again"; no command interpreted (nothing committed) |
| StartStep | executable not found | domain outcome | `StepStartFailed{not_found}` → build Failed; UI says which command and to install it or set it in the repo's build settings |
| StartStep | `platform.ErrBatchArg` (should be caught at save) | domain outcome | `StepStartFailed{bad_args}` |
| StartStep | dir missing (worktree removed) | domain outcome | `StepStartFailed{dir_missing}` |
| StartStep | log file can't be opened | domain outcome | `StepStartFailed{other}` with a message; the process is not started |
| process | non-zero exit | domain outcome | `StepExited{code}` → Failed |
| process | output cut after WaitDelay (`OutputTruncated`) | escape hatch | `LogTruncated` on the step; the step's outcome follows its exit code |
| process | ygg crashes or is killed | domain outcome (on restart) | the job object kills the tree; startup feeds `ProcessLost` → Interrupted |
| commit ok, crash before StartStep | — | domain outcome (on restart) | the build is `Running` with no process → `ProcessLost` → Interrupted |
| CollectArtifacts | glob/stat error | escape hatch | `ArtifactsCollected{}` with what was found; errors logged |
| Publish | slow client | escape hatch | the hub drops the client; it reconnects and refetches |
| Step | an input that is illegal for the state | domain outcome | no change, no commands (by construction) |
| Step | panic / invariant broken | die | recovered by the input goroutine, logged loudly, build left as stored; a property test should have caught it |

Error translation:

- sqlite error → `db.ErrConflict`/`db.ErrNotFound` (item 6) → `builds.Error{Class, UserMessage}` → api error class → HTTP (404/409/400/503).
- platform errors → `StartFailure` reasons. Callers never see `exec` or `windows` error types.

## Persistence and delivery

- **State:** the `builds`, `build_steps` and new `build_artifacts` tables. There is no event log, inbox or outbox (decision: `ProcessLost` instead of an outbox). Effects run only after `Commit` returns, never inside the transaction or the HTTP handler. The handler returns 202 once `Enqueue`/`Cancel` has committed.
- **Expected version:** `builds.version` is incremented on every `SaveBuild`. `build_steps` rows are rewritten with the build in the same transaction, so they need no version of their own. The review's per-step version is not needed, because steps are only ever saved with their build.
- **Migration `00002` (task B):** SQLite can't alter a CHECK constraint, so `builds` and `build_steps` are rebuilt (create new, copy, drop, rename, recreate indexes).
  - `builds`: add `version INTEGER NOT NULL DEFAULT 0`, `actor TEXT NOT NULL DEFAULT 'user'`, `created_at` kept (it is `QueuedAt`), `started_at TEXT`, `result_step INTEGER`, `preset_id TEXT`. Status adds `interrupted`.
  - `build_steps`: add `argv TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(argv))`, `attempt INTEGER NOT NULL DEFAULT 0`, `outcome TEXT` (`succeeded|failed|start_failed|cancelled|interrupted`), `start_failure TEXT`, `log_truncated INTEGER NOT NULL DEFAULT 0`. Status adds `skipped` and `interrupted`.
  - new `build_artifacts(build_id, repo_id, path, size, PRIMARY KEY (build_id, path))`.
  - new `build_presets(id, project_id, name, steps TEXT CHECK (json_valid(steps)), created_at, version)`.
  - `tasks` and `proposals` get `version INTEGER NOT NULL DEFAULT 0` too.
- **Event IDs:** inputs from users get no dedup ID. `Enqueue` is keyed by the generated `BuildID` (a duplicate insert → `ErrConflict`), and `Cancel` is idempotent by the transition table. Interpreter results are keyed by `(BuildID, Index, Attempt)`, and duplicates are no-ops (I5).
- **Timers:** none. No step timeout and no scheduled inputs at v1.
- **Unknown outcome:** `StartStep` is the only non-idempotent command. If ygg dies after commit but before or during the process, the outcome is unknown. The reconciliation is `ProcessLost` at startup: the job object guarantees the process tree died with ygg, so "interrupted" is always true.
- **Shell invariants (chaos tests: kill the service at each crash point, restart):**
  - S1: a step process starts at most once per `(BuildID, Index, Attempt)`.
  - S2: after startup reconciliation, no build is `Running` or `Cancelling` without a live process.
  - S3: at most one build is `Running` at any time (BL-03).
  - S4: no process of a build runs after its build is `Finished`.
  - S5: every started step has a log file, and no token from the test redactor appears in any log file or WS message.

## Boundary

| Source | Parser | Produces | Rejects |
|---|---|---|---|
| HTTP `POST /api/builds` JSON | `builds.ParseRequest(raw, repos)` | `corebuilds.Spec` | zero steps; >64 steps; unknown repo; worktree not belonging to the step's repo; empty argv; NUL in any arg; shell metacharacters (`platform.BatchArgsOK`, applied on every OS so presets stay portable); name empty or >200 runes |
| Preset save `POST /api/build-presets` | `builds.ParsePreset` | `corebuilds.Preset{ID, ProjectID, Name, Steps}` | same rules as above, plus a duplicate name in the project → domain outcome 409 |
| DB rows (`builds` + `build_steps` + `build_artifacts`) | `db.buildFromRows` | `corebuilds.State` + version | unknown status/outcome, missing argv for a started step, step count ≠ spec count, `Running` without exactly one running step → error (corrupt row: die, logged) |
| Preset row `steps` JSON | `db.presetFromRow` | `corebuilds.Preset` | same as ParsePreset |
| Process result | interpreter `exitInput(err, waitResult)` | `StepExited` / `StepStartFailed` | — (total function, classifies every error) |
| `pom.xml` | `maven.ParsePOM(r io.Reader)` (`encoding/xml`, no network, no parent resolution beyond the reactor) | `corebuilds.Module{RepoID, Coord, Deps []Coord}` | malformed XML, missing `artifactId`, documents over 4 MiB |
| `GET …/log?after=` | `parseOffset` | `int64 ≥ 0` | negative, non-numeric, > file size |
| WS topic `build:<id>` | `api.ParseTopic` (task C) + `BuildTopic` variant | `api.Topic` | invalid build ID |

Every row gets:

- a round-trip test (`parse(format(x)) == x`), except the process result, which is total;
- accepted ⇒ valid (`Spec.Validate()`/`State` invariants hold on everything accepted);
- one test per rejection rule;
- a fuzz target: `FuzzParseRequest`, `FuzzParsePreset`, `FuzzBuildFromRows`, `FuzzParsePOM`, `FuzzParseOffset`.

## Open questions

Approved by the human on 2026-10-18 with every recommendation below.

1. **Queued builds after a restart:** start them automatically when ygg comes back? *Recommend yes:* they were queued on purpose, and the UI shows them.
2. **Step timeout:** none at v1? *Recommend none.* Users cancel by hand. A timeout would need a `ScheduleInput` and a `TimedOut` outcome later.
3. **Maven cycles (BL-04 "handle circular dependencies"):** keep cycle members together in input order and show a warning, or refuse to order? *Recommend warn and order:* that matches "handle", and a build tool would fail loudly anyway.
4. **"One build at a time" scope:** global (as the PRD says), or per repo / per worktree? *Recommend global for Phase 2.* Revisit in Phase 4, when VF-01 verify runs in agent worktrees, by raising `max` or keying `Next` by target.
5. **History retention:** keep all builds and log files forever, or prune (e.g. the last 200 builds per project)? *Recommend* keeping everything in Phase 2 and adding pruning (as a proposal, never a silent delete) when it matters.
